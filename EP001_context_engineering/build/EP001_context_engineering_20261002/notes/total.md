# 01_hook

模型上下文窗口已经大到一百万 token,很多人由此得出一个直觉:把所有东西全塞进去就行了,反正装得下。这一页故意用一台吊车,把聊天记录、整个仓库、几百页 PDF 全倒进同一个集装箱,来挑战这个直觉——大窗口并不等于好上下文。所以整期只回答一个问题:一次模型调用之前,到底应该给模型看什么?

---

# 02_storage_context

先分清两层。系统里确实存了很多东西:对话日志、长期记忆、检索索引、Agent 状态、工作区、检查点,这些回答的是"系统知道什么"。但模型这一刻能看到的东西要少得多,它回答的是"模型此刻应该看到什么"。注意中间这道路径并不是全部涌上去,而是先经过一次筛选。特别强调一条边界:记忆、检索和历史只是 Context 的候选来源,它们本身不是 Context。

---

# 03_compiler

把刚才那道筛选画完整,就是整期的核心架构:Context Compiler。左边是八类候选,从系统策略、当前任务、状态、历史、工具结果、检索证据到记忆和工作区;中间的编译器做四件事——先筛掉无关和无权的材料,再按相关度和权威排序,然后在 token 预算内取舍,最后组装成本轮的模型输入;右边得到的才是模型可见的工作集。有两个关键点:它每次模型调用都运行一次,不是一份持久记忆;它的输出随任务阶段变化,既不是全部历史,也不是把窗口填满。

---

# 04_admission

那"有没有资格进入"到底怎么判断?看四张真实的候选卡。系统策略相关性只是中等,却必须进入,因为它是不可覆盖的安全与审批边界;最新的测试失败相关性高、时效新,直接决定下一步动作,也进入。而那条旧假设,相关性曾经很高,但状态已经被否定,失效压过相关性,留在库里;README 段落则因为和当前 Bug 无关被丢弃。所以进入的标准不是"有没有这个信息",而是它对当前决策有没有用,以及是否可靠。

---

# 05_dimensions

这个判断展开来是五道关卡:相关性、权威、时效、权限与来源、token 成本。重点不在记住这五个词,而在于它们会互相冲突。网页内容非常相关,但它不是系统指令;一条历史消息高度相关,但状态已经过期;一段代码很权威,却与当前 Bug 无关;一个工具结果很新,但权限已经被撤销。所以 Context Selection 不是一个单一的相关性排序问题,而是一个多维度、会冲突的取舍问题。

---

# 06_authority

其中最容易被忽略的一层值得单独讲:相关不等于有权。任务是修复登录 Bug,检索到一条与任务高度相关的评论——语义上它确实贴题,但它来自不可信来源,绝不能因为"相关"就升格为指令。左上角相反:内部编码规范很有权威,却与本轮无关,权威补足不了无关。Compiler 不只决定看什么,还必须保存每条材料是什么来源、应以什么权限来解释。

---

# 07_budget

有了资格判断,还要过预算这一关。把窗口想成一根预算条:系统指令、任务、工具契约和输出预留是相对刚性的部分,剩下的 Dynamic Context 才是历史、证据、代码、工具结果和记忆互相竞争的地方。屏幕上这个减法公式只是帮助理解预算关系的工程抽象,不是行业标准公式。记住一句话:窗口大小只是上限,有用的上下文是选择的结果。

---

# 08_agent_before

现在把整期概念放进同一个例子。这个 Coding Agent 要修复登录 Bug 并保证测试不回归,前五轮它搜过代码、查过中间件、提出过一条后来被否定的假设、跑过测试、确认了真正的堆栈。此刻系统里躺着十一种候选:用户目标、仓库策略、确认的堆栈、脏文件、相关鉴权代码、最新失败测试,也有效率很低的旧假设、重复的 shell 输出、一大堆无关文件和早期探索轨迹。问题来了:第 6 次调用,哪些进入?

---

# 09_agent_after

这是选择之后的样子。左边还是那个候选池,经过编译,真正进入本轮的只有七项:目标、策略、确认的堆栈、相关鉴权代码、脏文件与工作区状态、最新失败测试,以及一条必要的先前结论——注意必要历史是以"已核验结论"的形式进入,而不是全量对话。被留下的,是早期无关探索、重复输出、已否定假设、无关文件和过期假设。要说清楚的是:目标不是最少,而是在可靠性约束下,保留当前决策真正需要的充分信息。

---

# 10_bad_good

为什么费这么大力气做选择?因为同一个模型,喂给它不同的上下文,下一步就可能完全不同。左边这份:旧假设、五百行日志、过期测试结果、无关文件全文,还缺当前 Git 状态——模型很可能继续去修那个早就被排除的问题。右边这份:目标、边界、当前状态、最新证据和失败测试齐备——模型就能针对当前证据修改并验证。上下文质量直接决定 Agent 行为。

---

# 11_failures

"越多越好"在这个例子里会以三种方式坏掉。噪声:无关信息抢占注意力与预算,关键约束被挤出去,又慢又贵;过期与冲突:新旧测试结果并存、被否定的假设复活,模型基于过期状态行动;权威与来源混淆:注入文本被当成指令、未验证摘要被当成事实,导致越权动作或错误结论。这三种失败常常同时发生,而且没有一种能靠"再塞进更多信息"来解决。

---

# 12_compaction

那历史越来越长怎么办?压缩是一条正经出路:摘要、压缩、驱逐、按需重载,把长历史变回候选信息。但请看这条流水线的后两段——压缩产物仍然只是候选,仍然要重新经过 Context Compiler 才能变成模型可见的上下文。压缩控制增长,但它本身有损,权限和关键约束不能只靠一份未经验证的摘要来维持,所以 Compaction 只是手段,不是 Context Engineering 本身。它丢掉的到底是什么,值得单独做一期。

---

# 13_mental_model

回到最初那个一百万 token 的直觉,现在可以给出完整的回答。左边这条把历史一味追加的路已经走不通;右边是本期的结论:上下文是在每次调用前,把约束、任务状态、证据和工具编译出来的工作集。Context Engineering 不是把更多信息塞进模型,而是在有限预算、权限和可靠性约束下,把当前决策真正需要的信息,编译给模型这一轮去使用。
