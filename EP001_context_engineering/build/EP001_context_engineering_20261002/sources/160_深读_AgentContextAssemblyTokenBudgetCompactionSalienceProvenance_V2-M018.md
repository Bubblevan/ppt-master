>

## 阅读主线：把“历史”编译成下一步的输入

Context Engineering 不是把越来越多的对话逐轮追加给模型。它是一个每轮运行的上下文编译器：先确定本轮目标和安全边界，再找回和本轮决策有关的状态、历史与证据，给候选信息标注来源和权限，估算 token 成本，按优先级裁剪和排序，最后形成带版本和 provenance 的模型请求。编译结果是一次推理的工作集；对话日志、业务数据库、文档索引和 checkpoint 才是可以长期保存或恢复的事实来源。

Anthropic 的工程文章把 context 描述为模型推理时实际收到的 token 集合，并把 context engineering 概括为在有限窗口中持续筛选不断增长的信息空间。它强调目标不是装入最多内容，而是让有限上下文更有助于预期行为；这是一篇工程实践文章，适合作为设计心智模型，不应误读成所有模型都遵循同一个性能定律。[SRC-ANTHROPIC-CONTEXT-ENGINEERING-2025-001]

## M18-Q1｜Context Engineering、Prompt Engineering、Memory 和 RAG 分别负责什么？

**主答：**Prompt Engineering 主要讨论怎样表达指令、示例和格式要求；Context Engineering 的范围更大，负责每次推理时实际选择、组装、排序、压缩和维护全部可见信息。一个模型请求里除了系统指令和用户问题，还可能含有工具定义、MCP 能力、历史消息、检索片段、文件内容、结构化任务状态、图像或音频输入。即使提示词一字未改，只要工具清单、检索证据、历史窗口或任务状态改变，模型看到的决策环境就变了，输出行为也可能改变。[SRC-ANTHROPIC-CONTEXT-ENGINEERING-2025-001]

Memory 和 RAG 是信息管理机制，不等于当前 Context。Memory 指跨轮保存并在合适时机重用的用户或任务信息；RAG 指从外部语料按查询找回候选证据；Context assembler 则决定哪些记忆与证据要进入本次模型调用、以什么顺序和格式呈现。最重要的工程区分是“存储范围”和“模型可见范围”：数据库里有一万段材料，不表示每轮都应该塞给模型；模型 context 内出现一条“用户偏好”，也不表示它就是权威、最新且经用户确认的长期事实。

一个稳健的运行链可以这样理解：

~~~text
持久事实源 / 对话日志 / 文档索引 / 工具注册表
                         ↓
                任务条件化读取与权限过滤
                         ↓
          重排、冲突检测、预算分配与内容裁剪
                         ↓
      指令 + 当前任务状态 + 证据 + 相关历史 + 工具定义
                         ↓
                    本轮模型推理
~~~

面试时可以用一个 coding agent 的例子说明层次：完整 Git 仓库是外部数据源，symbol search 与 grep 是检索，用户要求“修复这个测试”是任务契约，AGENTS.md 与审批边界是指令，失败测试和相关函数是当前证据；最终 Context 只放与本轮修复有关的少数文件、约束和诊断，而不是仓库全量源码。另一轮可能只需测试输出与补丁差异，context 应随任务阶段变化。

**连续追问：Context Engineering 是否就是 Prompt Engineering 的新名字？** 不是单纯改名。提示词写法依然重要，但长程 Agent 的难题还包括检索、状态、工具结果、权限、上下文预算、压缩和多轮变化；这些需要系统组件共同负责。**上下文越长是不是越好？** 容量上限更大，只代表系统可以容纳更多 token；是否有帮助仍取决于模型、任务、信息相关性、位置、干扰与成本。Anthropic 的文章报告过长输入下的注意力和信息利用挑战，但具体退化幅度应在目标模型和任务上测量，不能跨模型直接外推。[SRC-ANTHROPIC-CONTEXT-ENGINEERING-2025-001]

## M18-Q2｜Context Window 的 Token Budget 应该怎样计算和预留？

**主答：**不要把 context window 当成“输入 prompt 字符数上限”。按当前 OpenAI Conversation State 文档的定义，一次请求的上下文窗口预算涉及输入 token、输出 token，以及适用模型上的 reasoning token；大文件、多模态输入、工具定义和消息包装也会占用模型请求容量。输出预算和推理预算必须保留，不能把模型标称窗口全部分配给检索文本。此处的具体范围和计数定义应依模型接口文档核验，不可用旧模型的例子代替当前目标模型合同。[SRC-OPENAI-CONVERSATION-STATE-2026-001]

做预算时，先把模型总窗口记作 W，把固定系统与开发者指令记作 S，把本轮用户输入记作 U，把工具 Schema 与 Agent 协议开销记作 T，把状态、历史和检索材料记作 D，把预留输出及 reasoning 的安全余量记作 R，则可用输入空间近似为：

~~~text
D_budget = W - S - U - T - R
~~~

如果调用还带图像、音频、视频帧、结构化 JSON、缓存前缀或供应商内部包装，最终要以目标 API 的实际 Token 计数/usage 字段为准；上式只是做预算治理的记账模型，不是模型 tokenizer 的精确公式。系统应将硬约束与软预算分开：硬约束是不能被裁剪的安全政策、用户目标、审批状态、工具权限与必要 schema；软预算是历史轮数、搜索候选数量、代码片段、网页原文和可展开背景。软预算不足时先压缩、重排或按需再取，不能悄悄删除硬约束。

预算要按阶段和工具返回量动态变化，而不是给所有轮次一个固定历史长度。例如 Deep Research 规划阶段可以减少网页原文、保留目标和研究子问题；证据综合阶段需要更多来源片段与冲突信息；最终写作阶段需要保留引用位置、结论限定词和用户要求的格式。Coding Agent 初次定位时可以给 repo map 与相关符号，执行测试后则应保留失败栈和相关改动，历史 shell 全输出可以保存到外部日志，只把摘要和可定位引用放进下一轮。

计算必须发生在最终 serializer 之后。原始字符串 tokenizer 可能遗漏 role 包装、工具 Schema、图像 token 化或供应商协议项；若先按字符预算截断，再由 SDK 添加几十个工具定义，系统仍会超窗。生产服务应按目标 model/provider 计数或保守估算，记录请求 usage、输入分项、输出预算和 overflow/截断事件，并在边界附近留有余量，应对工具结果膨胀、检索文档重复和多模态开销。[SRC-OPENAI-CONVERSATION-STATE-2026-001]

**连续追问：把输出上限设得很低能不能简单解决超窗？** 这只压低了生成端的预算，可能造成答案或工具参数截断，不能代替输入治理。**Token 计数估算差几个百分点要紧吗？** 若离窗口上限很远通常影响有限，但在长 prompt、多个并发 Tool Result 或长输出情况下，误差可能改变是否截断和任务是否完成，所以要按 P95/P99 负载留安全余量，并告警接近阈值的请求，而不是等 API 报错再处理。

## M18-Q3｜Context 中的消息和材料应按什么顺序组装？顺序是否等于信任等级？

**主答：**先分清两件事：指令的“权威层级”和内容的“序列位置”不是一回事。系统/开发者策略、用户请求、工具协议、检索资料、网页原文和代码注释应有来源标签和信任边界；不能假设把某段文本放到最后，就会让它拥有更高的业务权限，也不能假设模型会在任意长上下文里自动执行一套隐式优先级。Role、字段和消息结构应遵从目标模型 API 合同；应用还需要把不可覆盖的安全策略保留在受控指令层，并把外部资料明确标为不可信引用数据。

一种实用的组装顺序是：固定策略与响应约束；本轮用户目标和成功条件；与目标相关的权威任务状态和审批结果；必要的工具说明；经过权限过滤的证据；少量近期历史或已核验的决策摘要；最后是需要模型立即处理的具体问题。顺序应针对模型和任务做实验，而非背成所有厂商通用规则。稳定、常复用的前缀通常适合保持内容和顺序稳定，变化的用户请求与检索证据放在后部可减少不必要的前缀变动，也可能改善 prompt cache 命中，但缓存仍是性能优化，不是上下文的真实性或可靠性机制。[SRC-OPENAI-PROMPT-CACHING-2026-001]

设计 API 时应为每个 context item 保留至少这些元信息：来源 ID/URI、数据更新时间、适用范围、租户和 ACL 判定、内容 hash、原文跨度或行号、置信度/审核状态、过期时间、是否可以用于行动。进入模型时可显示短 source label 或 citation key；工具返回和 RAG chunk 不要与 system policy 混成一段无来源的自然语言摘要。若模型要对检索证据做动作，应由控制层复核动作权限和数据新鲜度，不应让“模型读到文本”本身升级授权。

**连续追问：如果工具结果出现在用户问题之后，是否会自动覆盖用户的指令？** 不会由序列顺序推导出可信度或授权；应用应按来源与类型解释字段，工具数据可以提供事实，却不能自行更改安全策略。**工具 schema 放在哪？** 它必须按 API 协议以模型可调用的工具格式提供；“人读起来放在 prompt 哪段更好”与“请求里 role/tool contract 如何编码”是两个层次。**不同模型是否同一顺序表现一致？** 不能保证，需用目标模型的分层评测固定模板版本，尤其测长上下文位置效应、冲突指令与工具选择。

## M18-Q4｜候选上下文如何排序和筛选？“最近发生的”是否优先级最高？

**主答：**“最近”只是一个特征，不能作为唯一选择策略。上下文条目的价值与本轮要做的决策相关：对当前任务是否有直接关联，来源是否权威、是否过期，是否能改变行动选择，是否包含强制约束或反例，是否有可核验出处，以及占用多少 tokens。可以把这些维度组织成一个打分启发式，例如：

~~~text
候选效用 ≈ 任务相关度 × 来源可信度 × 时间有效性 × 决策影响
            + 强制约束/新反证的优先权 - token 成本 - 冗余惩罚
~~~

它不是具有普适最优保证的公式。真正系统通常先处理 hard filters，再在剩余候选里按 query/task stage 做检索和重排，最后依据预算选择。授权、保密级别、有效期、用户撤权等应先作为硬条件过滤，不能靠相关性打分把无权限材料“排得低一点”后仍放进 context。

对 Research Agent，同一主题里可能同时有近期新闻、旧的官方规范、过时博客和互相矛盾的实验。最新页面不一定是规范事实，旧的技术标准也不一定已经失效；系统应保留主张、发布/生效日期、目标版本、来源类型与冲突点，让模型回答时说明适用条件。对 Coding Agent，当前工作树和测试日志常比之前一周的聊天更能决定下一步；但项目 AGENTS.md、用户明确限制和未完成审批属于高优先级约束，不会因为旧就能丢弃。

长上下文研究中，token 数越大并不保证有效信息越多。Anthropic 的工程经验建议以高信号 token 支撑预期行为，并讨论上下文过长带来的注意力和信息利用挑战；落地时应把它转成任务评测假设：对于本任务，加入更多材料是否改变证据召回、正确决策或引用完整性？如果没有提高，甚至增加冲突与成本，就不应因为“窗口还空着”而继续填充。[SRC-ANTHROPIC-CONTEXT-ENGINEERING-2025-001]

**连续追问：能否把所有材料统一算一个相关性分？** 通常不够。不可妥协的安全指令、ACL 和用户明确硬约束必须先保留；外部证据则要权衡来源、时效、冲突与任务阶段。**Memory 的 top-k 该设多大？** top-k 只是召回阶段参数，最终进入 context 的数量要由 token 预算、证据多样性和任务指标决定；对关键来源可用去重、coverage 和 citation recall 约束，避免大量相似片段挤掉反方证据。

## M18-Q5｜长对话和长任务应该使用完整历史、滑动窗口、摘要还是外部检索？

**主答：**这几种办法解决不同问题，生产系统通常组合使用。完整历史保留原始话语、时间顺序与精确措辞，适合上下文短、任务刚开始、用户刚给出细粒度约束时；缺点是增长快、重复多、旧噪声会抢占预算。滑动窗口保留最近几轮，方便维持局部对话连贯，但它会丢掉远端的重要决定或约束，不能假定旧内容都已过时。摘要和 compaction 降低重复信息的 token 成本，但有损、可能误概括；外部检索能按需取回很久以前的原文和记录，却增加索引、权限、排序与召回失败问题。

一个可运行的混合方案是把“精确事实”“当前状态”“完整原始轨迹”分别存放，再按任务装配。精确事实和用户同意记录在可审计状态源中，当前 action、未完成步骤、版本与审批放在 Task/Checkpoint；对话原文和 Tool Result 保持 append-only 或受治理的日志；摘要作为加速读取的派生视图，必须能回指原始消息或事件；RAG 与 Memory 检索按当前任务召回少量内容。下一轮的上下文由结构化状态和近期交互重建，必要时从日志、文档或代码库取回可验证细节。

请避免“摘要里写了，所以它就是事实”的错觉。摘要可能把“方案 A 待评估”缩成“采用 A”，把两个版本混成一个，或把推测改写成确定陈述。每个摘要事实宜携带原始来源、发生时间、是否已确认、有效范围和冲突关系；重要的金额、权限、版本、文件路径、未完成动作、用户拒绝和审计要求应保留结构化字段，而不是只押在自由文本摘要上。

**连续追问：summary 应由 LLM 每轮重写吗？** 未必。全量重写会带来成本、随机变化和反复漂移，可以采用增量摘要加定期全量校正；无论哪种方式，摘要写入前都要定义字段、冲突规则和来源回链。**如何处理用户修正历史？** 把新修正记录为有时间和作者的事件，更新当前有效投影，保留旧值及其失效时间以供审计；下一轮 context 只呈现当前有效事实和必要的纠正依据，而不是同时让模型看到两个无标注的矛盾值。持久事件和 checkpoint 的恢复语义见 M016–M017。

## M18-Q6｜什么时候 Compaction？压缩时必须保留什么，流程怎样设计？

**主答：**Compaction 是为当前任务把逐轮累积的上下文转换为较短、仍可继续工作的表示；它可以是服务端能力、客户端摘要、分层 summary，或删除旧消息并按需回载。不是每个请求都应压缩：短任务过早压缩只会损失引用和精确措辞；长任务在逼近预算时才触发可能已经来不及。触发条件应同时考虑当前 token 占用、预留输出、剩余任务复杂度、过去工具结果规模、压缩延迟与重建成本，而不是简单写死在“历史超过 N 轮”。

压缩前先把可恢复的事实提交到系统权威状态中，再生成压缩视图。候选摘要应保留：用户目标和成功标准；不可违背的限制、授权和拒绝；当前已确认结论以及来源；未完成子任务、阻塞点和下一步；已调用工具、外部副作用、幂等 key/receipt 或未知结果；相关版本、代码分支、文件和测试状态；检索引用、时间戳及证据冲突；最近的决策依据。重复解释、已解决的中间推理、冗长原始工具输出可以删除，但应保存日志定位 ID，以便需要时重新读取原文。

对于自建 compaction，可以按一个保守流程实施：一，预算器发现预测请求超窗或成本/延迟门槛；二，把当前状态、未决 action 和外部 side effect 做一次一致性读取；三，按字段 schema 生成候选摘要，并为每项附来源；四，运行确定性校验，例如必要字段、引用可解析、权限未扩大、数字/ID 没有无依据变更；五，构造“旧摘要 + 本轮新输入”或“checkpoint + 最近对话”的候选新 context；六，用关键事实回忆和任务继续测试比较压缩前后；七，只有通过后才原子切换到新版本，保存摘要版本与原文水位。遇到工具调用尚未确认、审批等待、并发写入或外部执行结果 unknown 时，不应压掉这些未完成事实。

OpenAI 当前 Responses API 文档给出的产品级示例包括服务器端 compact threshold 和单独的 compact endpoint。后者收到完整上下文，返回压缩后的窗口，其中可能有不透明的加密 compaction item，也可保留旧窗口条目；官方说明要把 endpoint 输出作为 canonical next context 原样传递，不要自行裁剪。此行为仅是该 API 的合同，不能推广成所有 Agent Framework 的通用语义。[SRC-OPENAI-COMPACTION-2026-001]

**连续追问：为什么不等 API 真报超窗再 compact？** 因为压缩请求本身也要接收当前上下文，不能超过可处理窗口；并且失败后再恢复需要读取原始历史，可能已经多花一次调用。应基于实际序列化后的 token 预测提前触发，并留下完整输入/状态供重试。**Compaction 是否等价于 checkpoint？** 不是。Compaction 改变模型可见材料；checkpoint 保存可恢复的工作流状态。摘要可以丢失信息，checkpoint 应按恢复合同持久化必要状态。两者可引用同一个事件水位，但职责不能混淆。

## M18-Q7｜怎样判断 Context 压缩过度，怎样量化信息损失？

**主答：**“摘要看起来通顺”不是正确性标准。过度压缩最危险的表现通常是约束丢失、来源丢失、时间范围变成最新事实、未完成 action 被写成已完成、条件句变绝对句、未知 outcome 被猜成成功、旧状态复活，以及反例和少数证据被主结论挤掉。通用语义相似度或摘要 Rouge 分数只能反映文字重合，无法回答这些任务关键事实是否保住了。

先为每类任务定义 preservation invariants，再建立由原始轨迹生成的验证样例。例如研究任务至少检验目标问题、纳入/排除条件、来源 ID、冲突证据、当前结论和不确定性；Coding Agent 至少检验用户禁止修改范围、当前 branch/dirty files、失败测试、最近 patch、未运行测试和待做动作；审批工作流至少检验授权主体、批准范围、金额/资源边界、到期时间和操作 receipt。压缩后让模型在不看原文的情况下回答一组已知必要事实，同时由确定性检查器核对 ID、版本、权限和状态字段。

建议至少记录四类指标：信息保留率（原轨迹中 task-critical facts 有多少仍可正确恢复）、证据忠实度（摘要 claim 能否定位到原文及是否保留限定条件）、后续任务效用（压缩后任务成功率、质量与回归失败率）、压缩成本（输入/输出 token、延迟、重新检索成本）。还应纳入冲突保留率、过期状态误用率、敏感数据泄漏率以及压缩失败恢复率。多种压缩比例、不同轨迹长度、工具类型、语言和对抗样例都要覆盖，报告置信区间或至少分层样本量；只看均值可能掩盖极少但高危的状态错误。

线上可安排 shadow compaction：对同一输入并行生成候选摘要，但真实请求仍用旧路径；通过离线 gold facts、审计标签和工具执行模拟比较后再灰度切换。可以在最终压缩前额外做“关键事实盘点”与“摘要差异审查”，但不要通过重复喂整个历史来验证，否则会失去压缩的意义。保留原始来源或可重放水位，才能在发现摘要错误时定位哪轮数据造成信息损失。

**连续追问：如何发现模型已经忘了某个约束？** 不能只观察模型主动提起。构造必须触发该约束的后续问题和动作，例如问它能否修改某个文件、发送某封邮件或引用某一版本，并检查决策是否遵守。**token compression ratio 越高越好吗？** 不是。压缩率只是效率指标；必须与任务成功、约束保留、引用忠实和严重错误率一起解释。对安全边界或副作用状态，应对极低丢失率要求更严格，而非接受更高压缩换取少量 token。

## M18-Q8｜previous_response_id、Compaction、自定义摘要和 Prompt Cache 有什么区别？

**主答：**它们分别解决会话续接、上下文缩减、自定义信息提炼和重复前缀成本问题，不应互相冒充。

| 机制 | 主要解决的问题 | 系统要负责什么 | 关键限制 |
|---|---|---|---|
| previous_response_id | 用响应 ID 延续有状态 API 对话 | 管理 response lineage、持久化要求和不可用时回退路径 | 不能凭 ID 假设输入 token 免费或窗口无限增长 |
| API Compaction | 把较大的模型 context 转成供应商可继续处理的较短窗口 | 按具体 API 合同传入/接收正确的 items，保存合适水位 | 输出可能含 opaque item；字段和兼容范围需按供应商版本核验 |
| 自定义摘要 | 提取业务所需状态、目标、证据和未决事项 | 定义 schema、来源回链、校验、版本和错误恢复 | 可移植可审计，但摘要模型可能遗漏、误写或产生幻觉 |
| Prompt Caching | 降低相同 prompt 前缀重复处理的延迟或输入成本 | 稳定前缀结构、监控真实缓存 token 与成本 | 缓存命中不保证、不改变 context 容量或持久状态 |

OpenAI Conversation State 文档明确指出，previous_response_id 可让 Responses 串接前一响应，但该链中先前的输入 tokens 仍会被计作输入 tokens；如某个 uncached response ID 无法解析，调用方要用完整输入 context 另开一轮。OpenAI Compaction 文档则区分 server-side threshold 与 standalone compact endpoint，并要求 standalone 输出完整原样传入下一次 Responses 请求。请勿套用这些参数或加密 item 到其他供应商。[SRC-OPENAI-CONVERSATION-STATE-2026-001][SRC-OPENAI-COMPACTION-2026-001]

Prompt cache 只缓存可复用的前缀计算，系统不能把命中当作会话记忆、持久化、授权校验或消除窗口消耗的保证。OpenAI 的文档说明，session 复用 context 不保证 cache hit；Compaction 也会改变请求前缀，压缩后第一次请求即使逻辑上相近，也可能复用更少的前序缓存。监控 usage 中缓存 token、总输入、cache write、延迟与真实费用，而不是只依据“我们每轮都复用 session”推断缓存有效。[SRC-OPENAI-PROMPT-CACHING-2026-001]

**连续追问：该选供应商 compaction 还是自建摘要？** 若依赖特定模型 API 并且想延续其上下文表示，可先验证官方 compaction；若必须跨模型迁移、给人工审核、显式保存业务状态或按 ACL 决定持久内容，就应有自有结构化 state 与来源化摘要。两种机制可以并存：业务 checkpoint 负责权威恢复，供应商 compaction 负责本轮模型上下文的紧凑表示。**开了 Prompt Cache 还要 context budget 吗？** 要；缓存不会把 prompt 从模型输入中移走，也不使超出窗口的请求可执行。

## M18-Q9｜如何处理 Context 中的过期事实、互相矛盾的材料和 Prompt Injection？

**主答：**把 context 看作“附带来源与授权状态的数据”，而不是把混在一起的文字当作一份天然可信的事实。每个 item 要带来源、采集/更新时间、适用版本、租户、ACL、数据类别、过期状态与是否经人工确认；整理冲突时，按事实域选权威源，例如用户当前明确更正覆盖旧偏好、项目当前 Git 状态覆盖陈旧聊天、官方版本化文档用于确认某 API 合同，业务数据库用于当前订单状态。时间新旧只有在同一事实域和同一权威级别下才有可比意义。

如果两个高可信来源给出不同结论，不要把它们平均成一条模糊结论，也不要悄悄选择对模型最顺眼的一条。保留两条主张、各自日期和范围，标为待核验并向用户澄清；对允许继续的分析，可以明确说明假设和结论依赖于哪个版本。对于会付款、改文件、发邮件、授予权限、发布代码等副作用，模型不应只凭 context 里不确定的摘要采取动作，应要求权威状态复查、工具端校验、用户确认或领域 policy gate。

外部网页、issue、代码注释、README、PDF、检索结果和用户上传文件中都可能带指令样式的 Prompt Injection。它们进入 context 后只能作为待分析数据，不能变成 system/developer policy。应使用结构化封装或明确边界标记，限制工具权限和网络/文件范围，降低可疑文本对执行决策的影响，使用独立 policy check 验证 tool arguments，并对敏感动作做审批。来源标签能辅助模型理解事实出处，但不能单独防止 prompt injection；强制权限必须在模型外执行。

ACL 应在检索阶段和生成/使用阶段都受控。多租户场景优先在检索前用 tenant/document ACL 限定候选，避免跨租户材料因语义搜索先进入共享 prompt；再对返回的 chunk 做权限复核和输出过滤。用户撤权或文档删除时，要让索引、缓存、摘要和派生记忆同步失效，否则旧内容可能从其他路径重新进入 context。被授权读取也不一定授权让模型使用它执行外部动作，需要把 data access 与 action permission 分成两个门槛。

**连续追问：摘要里引用了旧文档，是否把来源 ID 留住就安全？** 不安全，来源 ID 只能帮助追溯；仍需检验权限是否还有效、版本是否正确、文档是否已撤权或更新、摘要 claim 是否忠于原文。**发现注入文本以后是否一律丢弃整个网页？** 看任务风险与解析能力。可以隔离可疑指令、只抽取经验证的事实段落并保留 provenance；高风险流程应拒绝或交给人工，而不能让“引用来源看起来正规”覆盖实际安全评估。

## M18-Q10｜如何设计 Long-running Deep Research 或 Coding Agent 的 Context Assembler？

**主答：**可以把 Context Assembler 当作带版本的编译服务，其输入是当前 Task/Run、身份与权限、模型/工具配置、状态水位和任务阶段；输出是实际模型请求、组成清单、token 账单和一个可审计的 context manifest。它不能只返回一段拼接好的字符串，否则线上发生遗漏、泄漏或 token 激增时，很难说明是哪条数据从哪来、为什么入选、被谁授权。

一个相对完整的执行过程如下：

1. **解析目标并生成任务契约。** 固化用户目标、成功条件、语言与格式、硬限制、截止时间、可用工具、预算、拒绝/审批要求和运行身份。
2. **加载权威状态。** 读取 Task/Run/Checkpoint 的当前 revision、未完成子任务、动作 ledger、取消/审批信号、schema/workflow version。并发恢复时用 M017 的 revision/fencing 语义避免读取旧 worker 的陈旧视图。
3. **构造候选集。** 从最近对话、长期记忆、检索索引、repo map、工具结果和项目指令取候选；先做 tenant ACL、删除/撤权、时间有效性、来源类型和内容大小检查。
4. **按任务阶段重排与去冗余。** 用任务相关度、权威性、时效、决策影响和证据覆盖选择；保留冲突材料与反例，合并重复片段时不能合并掉来源。
5. **分配动态 Token Budget。** 保留固定策略、当前目标、必要状态、工具契约和模型输出余量；对软材料分桶或压缩。通过目标 provider/model 的 tokenizer/usage 估算最终请求成本。
6. **生成有类型的消息/内容项。** 指令、用户要求、任务状态、外部证据、工具输出和多模态内容分开编码；外部材料显式标为引用数据，tool 权限独立由控制层执行。
7. **运行确定性和安全校验。** 检查必需字段、来源回链、越权材料、冲突、超预算、待审批动作、压缩水位以及是否把 unknown side effect 错写成完成。
8. **提交请求并记录 Manifest。** 保存 context version、policy version、模型名、token 估算与真实 usage、候选 item IDs 与入选原因、被裁剪项目、compaction version 和输出关联 trace；敏感正文按保留策略处理，不能默认把所有用户数据复制进日志。
9. **根据反馈更新而非盲目追加。** 新一轮基于工具结果和状态增量重编译；当模型指出缺证据时做定向检索；当 context 逼近阈值时执行经过验证的压缩；用户取消或撤权后立即改变可用状态与材料。

以 20 分钟 Deep Research 为例，规划阶段重点保留问题拆解、范围、查询覆盖和停止条件；搜索阶段保留已访问来源及增量发现；证据合成阶段重点保留逐条 claim/source 对应关系、矛盾证据和版本；写作阶段把证据 manifest 与用户格式要求组装好。以 Coding Agent 为例，规划阶段加载 repo map、git 状态和项目指令；定位阶段按 symbol/test 召回代码；修复阶段关注必要文件、报错和补丁；验证阶段必须保留最近 test/build 输出、未测试声明和改动差异。阶段切换时的输入分布不同，因此采用阶段条件化预算比固定“最近 N 轮”更可靠。

评测至少要覆盖：Context 超窗/截断率、P50/P95/P99 输入 token、任务成功率、关键约束保留率、citation precision/recall、冲突识别率、上下文新鲜度、压缩事实丢失率、敏感信息越权率、Tool argument validity、单位任务成本与缓存命中后的真实成本。按任务类型、任务长度、工具数、租户权限、压缩比例和模型版本分层报告，并保留盲测/回归集。若做 A/B，固定数据与工具状态，按任务成对比较，控制模型随机性和外部环境变化；不要把“prompt tokens 下降”单独当作 Context Engineering 成功。

**连续追问：Manifest 要不要存所有 prompt 正文？** 先按威胁模型和隐私合同决定。一般可以先存 item ID、内容 hash、来源 URI、token 数、入选/裁剪理由与版本；受控审计、排错确有必要时再对特定字段加密保存正文和访问审计。**怎么处理组装失败？** 不应静默删除政策或用户硬约束来凑 token。按安全优先级返回可解释错误、降低候选数量、定向重检索、要求用户缩小目标、转入分阶段任务或改用支持长上下文/异步处理的部署。**这套系统最容易被忽略的测试是什么？** 长任务中间用户改目标、资料撤权、工具产生超大输出、response chain 不可解析、摘要与状态版本不一致、跨租户结果意外混入，以及取消和 compaction 同时发生。

## 本章复习框架

回答 Context 问题可以沿着五个层次展开：第一，声明当前任务与不可丢约束；第二，说明信息来自什么权威源、何时有效、是否可见；第三，描述候选检索、排序和 token 预算如何协同；第四，说明 compaction/摘要的可逆边界、来源追溯和损失检测；第五，给出模型接口、评测、故障恢复和安全控制。只有“把最近聊天截断到 4k tokens”不构成完整设计，因为它没有说明重要事实、权限和外部动作怎么保留。
